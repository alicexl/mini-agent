## 第 1 章 demo5 干了什么

### 【口播 · 开场】

demo1 的 ReAct 循环在单个 Agent 内部运作——messages 是一条线性流水。两个问题：

1. **相互独立的子任务**——「统计文件数 + 计算 + 查天气」互不相干。主 Agent 不关心子任务怎么做，只关心结果。但单 Agent 模式下，每个子任务的工具调用、错误、重试全塞进主 Agent 的 messages，上下文快速膨胀；即便用压缩或记忆机制，相关与不相关的细节也被**同等压缩**，无法区分对待
2. **需要多角色协作的任务**——多个不同角色、多轮交互，单 Agent 既无法角色分工，也没有让任务在角色间流转的机制

所以 Agent 需要两个能力：**独立子任务的分包执行**（Subagent）+ **多角色分工协作**（Team）。

> ### demo5 = base × 多 Agent

demo1 的核心没动——ReAct 循环、四个本地工具、messages 结构全原封不动。只在上面加了两条机制，分别在两个文件里：

- **`agent_sub.py`**——加 `subagent` 工具，主 Agent 遇到独立子任务时派一次性 Subagent，干完即销毁
- **`agent_team.py`**——加 `Agent` 类（持久对象 + `self.messages`）+ `Team` 类（消息队列协调器）+ `plan_team` 工具（LLM 只拆角色，任务由用户原始输入驱动）+ `get_weather` 教学模拟工具（返回模拟天气数据，让天气调研员角色有真实工具可调，演示 `[send:]` 路由）

Subagent 和 Team 的设计哲学不同：

- **Subagent 是"无状态的外包工"**——独立 context，干完即销毁，主 Agent 只看到结果摘要
- **Team 是"有状态的项目组"**——持久对象 + 消息队列 + `[send: 成员名]` 路由，成员间可转交任务

接下来两章分别拆解。

## 第 2 章 机制一：Subagent（一次性外包）

### 【口播 · Subagent 是什么】

Subagent 的作用很简单：让主 Agent 把一个独立子任务"分包"给一个临时 Agent，临时 Agent 用自己独立的 messages 干完，把结果摘要交回来就销毁。

听起来很朴素，但它的本质是**给主 Agent 减负**：

- 主 Agent 的 messages 不再被无关子任务的中间结果污染
- 每个 Subagent 用全新 context 专注一件事——做完就销毁，不占内存
- 多个独立子任务可以派多个 Subagent（主 Agent 看到的只是 N 段结果摘要）

### 2.1 subagent 工具的定义

### 【屏显 · 代码 3-1 — subagent 工具定义】

```python
{
    "name": "subagent",
    "description": (
        "委派一个独立的 Subagent 完成子任务。Subagent 有独立的 context（messages），"
        "执行完返回结果摘要后即销毁。主 Agent 不关心子任务怎么做，只关心结果。\n\n"
        "**使用时机**：相互独立的子任务——每个子任务派一个 Subagent。"
        "链式任务（后一步依赖前一步结果）不要用，Subagent 之间无法传递结果。"
    ),
    "input_schema": {
        "type": "object",
        "properties": {
            "role": {"type": "string", "description": "Subagent 的角色，例如「Python 工程师」/「文件统计员」"},
            "task": {"type": "string", "description": "交给 Subagent 完成的具体任务描述"},
        },
        "required": ["role", "task"],
    },
}
```

### 【口播 · description 的关键设计】

description 里有两段引导，决定 LLM 何时用、何时不用：

1. **正向触发**：「相互独立的子任务 → 派 Subagent」
2. **反向抑制**：「链式依赖任务 → 主 Agent 自己顺序做」


### 2.2 subagent 和 base 工具一样——都在路由表里

### 【屏显 · 代码 3-2 — 路由表含 subagent】

```python
AVAILABLE_FUNCTIONS = {
    "execute_bash": execute_bash,
    "read_file":    read_file,
    "write_file":   write_file,
    "edit":         edit,
    "subagent":     subagent,
}
```

### 【口播 · subagent 就是普通工具】

和 demo4 的 plan 一样，subagent 也在路由表里。唯一的特殊逻辑在 `subagent()` 函数内部——启动子循环时过滤掉自身防递归。主循环不需要任何特殊拦截。


### 2.3 共用 `_react_loop`：主循环和子循环同构

### 【屏显 · 代码 3-3 — _react_loop 的签名】

```python
def _react_loop(
    messages: list,              # 该循环专属的 messages
    tools: list,                 # 本循环 LLM 能看到的工具列表
    local_fns: dict,             # 本循环可调用的本地函数字典
    system_prompt: str,          # 本循环的 system prompt
    depth: int,
    verbose: bool,
    indent: str = "",            # 打印缩进，让 subagent 轨迹嵌套可视化
) -> str:
```

### 【口播 · 主循环和子循环的差别只在三个参数】

这是 demo5 最关键的设计——**主 Agent 和 Subagent 跑同一个 `_react_loop`**，差别只在传入的参数：

| 参数 | 主 Agent | Subagent |
|---|---|---|
| `messages` | `[{"role":"user","content":user_input}]` | `[{"role":"user","content":task}]`——**全新一份** |
| `system_prompt` | 基础 system prompt | 角色化 f-string——**只拼角色** |
| `tools` | `ALL_TOOLS`（含 subagent） | 去掉 subagent 的过滤版（**防递归**） |

**核心洞察**：Subagent 的"独立性"不是靠新写一个循环，而是靠**传入独立的 messages/prompt/tools**。同一个 ReAct 循环，喂不同的 context，就是不同的 Agent。

### 2.4 `subagent()` 的实现

### 【屏显 · 代码 3-4 — subagent 函数】

```python
def subagent(role: str, task: str) -> str:
    tools = [t for t in ALL_TOOLS if t["name"] != "subagent"]   # ① 去自身防递归
    indent = "    "

    sub_messages = [{"role": "user", "content": task}]          # ② 独立 messages
    sub_system_prompt = f"你是一个被委派来的 Subagent。角色：{role}。"  # ③ 独立 prompt

    final = _react_loop(messages=sub_messages, tools=tools, ...)

    return f"[Subagent · {role}] 任务：{task}\n结果：{final}"    # ④ 用完即销毁
```

### 【口播 · 关键设计】

1. **独立 messages**：局部变量，函数返回即销毁——主 Agent 拿不到 Subagent 的内部对话
2. **独立 system_prompt**：角色化 f-string，只拼角色
3. **工具集去 subagent**：在 `subagent()` 函数内部现场过滤 `tools = [t for t in ALL_TOOLS if t["name"] != "subagent"]`——Subagent 看不到 subagent 工具，堵死递归
4. **一次性**：函数返回字符串，`sub_messages` / `sub_system_prompt` 随之销毁——下次主 Agent 再调 subagent，又是全新一份

### 2.5 真实案例：三个独立子任务 → 派三个 Subagent

### 【屏显 · 实测日志 3-1 — agent_sub.py 真实运行】

**用户输入**：

> 我需要你做几件事：1) 统计目录下所有 py 文件的个数；2）计算 39 × 48；3）查询北京的天气

**实测轨迹**：

```
主 Agent 第 1 轮:
  LLM 识别出 3 个独立子任务 → 依次派发 3 个 Subagent

  [Subagent · 文件统计员] 任务: 统计 .py 文件个数
    → execute_bash("find . -name '*.py' | wc -l")  → 1
    → execute_bash("find . -name '*.py'")           → ./agent.py
    → 结果: 共 1 个 .py 文件

  [Subagent · 计算器] 任务: 计算 39 × 48
    → execute_bash("echo $((39 * 48))")  → 失败（bash 语法不兼容）
    → execute_bash("python3 -c ...")      → 失败（无 python3）
    → execute_bash("awk '{print $1*$2}'") → 1872
    → 结果: 39 × 48 = 1872

  [Subagent · 天气查询助手] 任务: 查询北京天气
    → execute_bash("curl -s 'wttr.in/Beijing?...'") → 真实天气数据
    → 结果: 局部小雨，25°C，湿度 94%

主 Agent 第 2 轮: end_turn → 汇总三个结果
```

（完整日志见屏幕。）

### 【口播 · 关键观察】

- **LLM 自动识别独立子任务**——3 个互不相干的编号任务，自动为每个派 Subagent
- **Subagent 独立 context、用完即销毁**——每个 Subagent 的内部 messages 对主 Agent 透明
- **Subagent 自动容错**——计算器 Subagent 连试 3 种方法（bash/awk → python3 → awk）才成功
- **主 Agent 只迭代 2 轮**——派发 + 汇总，中间所有工作都在 Subagent 内部

这就是 Subagent 的核心价值——**主 Agent 的 messages 保持干净**，所有子任务的中间结果都隔离在 Subagent 内部，结束后只留一段摘要。

## 第 3 章 机制二：Team（持久项目组）

### 【口播 · Subagent 的痛点】

Subagent 解决了"独立子任务分包"的问题，但遇到**需要多角色协作**的场景就力不从心：

1. **用完即销毁**——不能累积记忆，同一个角色被多次唤起时每次从零开始
2. **不能互相通信**——A 的结果只能传回主 Agent 再转述
3. **没有多角色分工**——自己写自己审，角色切换全靠 messages 里"现在我是 XX"

**Team 的升级**：把"一次性函数"升级为"持久化对象 + 消息队列协调器"——Agent 有 name/role/messages，可被多次唤起；Team 维护消息队列，成员通过 `[send: 成员名]` 协议把任务转交给最合适的人。LLM 只拆角色，任务由用户原始输入驱动。

### 3.1 plan_team 工具定义

### 【屏显 · 代码 3-1 — plan_team 工具】

```python
{
    "name": "plan_team",
    "description": (
        "为复杂任务组建多角色团队。你只需要规划角色（role），"
        "任务由用户原始输入驱动，不需要你拆。\n\n"
        "**使用时机**：需要多角色分工的复杂任务。"
        "简单任务直接用其它本地工具完成。"
    ),
    "input_schema": {
        "type": "object",
        "properties": {
            "task": {"type": "string", "description": "用户原始任务（可选，传给第一个成员）"},
            "members": {
                "type": "array",
                "items": {
                    "type": "object",
                    "properties": {
                        "name": {"type": "string", "description": "成员英文名"},
                        "role": {"type": "string", "description": "角色描述（简短，10字以内）"},
                    },
                    "required": ["name", "role"],
                },
            },
        },
        "required": ["members"],
    },
}
```

和 subagent 一样，LLM 自主判断何时用。**关键差异**：subagent 让 LLM 同时给 `role + task`；plan_team 让 LLM **只拆角色**，任务由用户原始输入整体驱动、传给第一个被唤醒的成员。

### 3.2 plan_team 的实现

### 【屏显 · 代码 3-2 — plan_team 函数骨架】

```python
def plan_team(members: list, task: str = "") -> str:
    if not members:
        return "[Team] 成员列表为空"

    team = Team()
    for m in members:                              # ① 阶段一·招募：注册到 registry
        team.recruit(m["name"], m.get("role", "团队成员"))
    team.initialize()                              # ② 阶段二·初始化：registry 完整，统一构建 system_prompt

    # ③ 随机挑一个起手——不匹配就 [send:] 转交，展示任务流转
    first = random.choice(members)
    team.send("用户", first["name"], f"你的角色是：{first['role']}。\n\n任务：{task}")

    return team.run(members)                       # ④ 消息队列事件循环
```

### 【口播 · 三步】

1. **招募（recruit）**：逐个把成员注册到 `registry`，**此时不构建 system_prompt**——因为 recruit 是逐个的，第一个成员注册时名册还不全，这时候拼 prompt 拿到的是残缺名册。
2. **初始化（initialize）**：全员注册完后（registry 完整）统一构建 system_prompt，让每个 Agent 都看到**完整团队名册** + 两条规则（只做本职；非本职就 `[send: 成员名]` 转交）。这就是拆成 recruit + initialize **两阶段**的原因——把「注册」和「拼 prompt」分开，保证拼 prompt 时名册一定完整（旧做法在 `Agent.__init__` 里直接拼 prompt，第一个构造的 Agent 名册就是残缺的）。
3. **随机起手 + 队列执行**：`random.choice` 选一个成员把任务丢进去，`team.run()` 跑事件循环。

为什么**随机**起手？——为了展示 `[send:]` 路由。如果总让"对的"成员起手，就看不到任务在成员间流转；随机起手，起手成员发现不是自己的活，就在回复开头写 `[send: 合适的人]`，由队列转发过去。

### 3.3 Agent 类：持久对象 + `[send:]` 路由

### 【屏显 · 代码 3-3 — Agent 类骨架】

```python
class Agent:
    def __init__(self, name, role):
        self.name = name            # 固定身份
        self.role = role
        self.messages: list = []    # 长期记忆，跨多次 chat 累积
        self.system_prompt = ""     # 留空——由 Team.initialize() 在全员注册完后统一构建

    def chat(self, event=None) -> str:
        # event → 把"[来自 X 的消息] Y" 作为 user 消息追加进 self.messages
        # 跑 ReAct 循环（工具集去掉 plan_team 防递归）
        # 返回最终文本（可能以 [send: 名] 开头 → 交由 Team.run 解析转发）
        ...
```

### 【口播 · 两条规则】

system_prompt 给每个 Agent 两条规则：

1. **只做本职**——只完成属于自己职责范围内的工作，不越权代劳别人的活
2. **非本职转交**——`[send: 成员名]` 是**字面协议标记**，不是自然语言。只要任务里还有不属于自己职责的部分（刚接手的、或本职做完后剩余的），回复**第一行**就必须是 `[send: 成员名]`（名册里的成员英文名），后跟一句转交说明；不要用「转交给 X」之类的自然语言或加粗替代，也不要顺手把别人的活做了。只有整个任务都落在自己职责内时才做完并结束

这样每个 Agent 各司其职，避免某个角色把所有活都包揽（否则其他成员永不参与、Team 退化成单 Agent）。注意 Agent 自己**不直接调用**其他成员——它只在回复里写 `[send:]` 标记，由 `Team.run` 解析后转发。这把"路由决策"留给 LLM，"路由执行"留给协调器。

### 3.4 Team 类：消息队列协调器

### 【屏显 · 代码 3-4 — Team 类骨架】

```python
class Team:
    def __init__(self):
        self.agents: dict = {}      # {name: Agent}
        self.registry: dict = {}    # {name: role}
        self.queue: list = []       # Event 队列

    def recruit(self, name, role): ...               # 阶段一·只注册，不拼 prompt
    def initialize(self): ...                        # 阶段二·registry 完整后统一构建 system_prompt
    def send(self, sender, receiver, message): ...    # Event 入队

    def run(self, members) -> str:
        # pop event → agent.chat(event) → 用正则扫描回复里的 [send: 名]
        #   有 → 把 [send:] 之后的内容转给目标成员（继续入队）
        #   无 → 不转发，等队列自然排空
        # 返回最后一条结果
```

### 【口播 · 事件循环】

`run()` 是事件循环：从队列 pop 一条消息 → 交给对应 `Agent.chat` → 用正则**扫描整条回复**里有没有 `[send: 名]`。有就把 `[send:]` 之后的内容转交给目标成员，没有就让队列自然排空。最后返回最后一条结果。

**为什么 `re.search` 扫全文，不是 `re.match` 只看开头？**——LLM 不总把转交标记写在第一行，常常先分析一通再决定转交（"我先理一下分工……`[send: X]`"）。只看开头会漏掉，所以协调器扫描全文做兜底。普遍教训：**协议解析不能假设 LLM 严格遵守格式**，解析侧要鲁棒。

> **路由稳定性依赖模型能力**。`[send:]` 触发靠 LLM「做完本职后主动写标记转交剩余」——在指令遵循较弱的模型（如 glm-5.2）上时灵时不灵：有时成员口头说"请查收"却不写标记，链断在某一环，`team.run` 返回的就是半成品。机制本身没错，换更强模型（如 Claude）会更稳。这恰好说明「LLM 决定路由」的代价：灵活，但受模型能力制约。

| 维度 | Subagent | Agent |
|---|---|---|
| **本质** | 函数 `subagent()` | 对象 `class Agent` |
| **生命周期** | 一次性，返回即销毁 | 持久，可多次 `chat()` |
| **messages** | 局部变量，函数返回即销毁 | `self.messages` 跨多次 chat 累积 |
| **通信** | 无，结果只回主 Agent | `[send: 名]` 路由，成员间可转交 |

### 3.5 真实案例：多角色团队 → `[send:]` 路由流转

### 【屏显 · 实测日志 — agent_team.py 真实运行】

**用户输入**：

> 帮我组建个团队调研下北京的天气并写出行建议

**实测轨迹**（LLM 拆出 Alice / Bob / Carol 三角色，随机起手 Carol）：

```
主 Agent 第 1 轮:
  plan_team(members=[Alice·天气调研员, Bob·出行顾问, Carol·报告撰写员],
            task="调研北京的天气情况并撰写出行建议")

  [Team] 消息队列启动：['Alice', 'Bob', 'Carol']

  [event] 用户 → Carol（随机起手，非对口）
  [event] Carol 完成：[send: Alice] 需要你先调研天气，提供数据后我来撰写报告
  [send] Carol → Alice

  [event] Carol → Alice
    [Alice] get_weather({"city":"北京"}) → 模拟天气数据
  [event] Alice 完成：[send: Carol] 天气数据已获取，供你撰写报告
  [send] Alice → Carol

  [event] Alice → Carol（拿到天气，识别「出行建议」属 Bob 职责，不自己写）
  [event] Carol 完成：[send: Bob] 天气数据已有，请给出出行建议
  [send] Carol → Bob

  [event] Carol → Bob
  [event] Bob 完成：[send: Carol] 出行建议如下，供你整合进报告
  [send] Bob → Carol

  [event] Bob → Carol（素材齐全，整合最终报告）
  [event] Carol 完成：# 📋 北京天气出行建议报告 ...（完整报告，不再 [send:]）

主 Agent: [循环结束] plan_team 已返回团队成果，直接汇报
```

（完整日志见屏幕。）

### 【口播 · 关键观察】

- **随机起手照样跑通**——Carol（报告撰写员）被随机选为起手，第一件事就是 `[send: Alice]` 把天气调研转出去，证明路由协议不依赖"对的"人起手
- **成员各司其职、不越权**——Carol 拿到 Alice 的天气数据后**没有顺手写出行建议**，而是识别出那属于 Bob 的职责就 `[send: Bob]` 转交（system_prompt 两条规则生效）
- **持久 Agent 累积上下文**——Carol 被唤醒 3 次（起手 / 收天气 / 收出行建议），`self.messages` 一直在累积，最后整合时能引用 Alice 和 Bob 的输入
- **plan_team 是终端调用**——团队跑完，主 Agent 直接把 Carol 的最终报告汇报给用户，不进下一轮（控制流截断，非 prompt 引导）

> **关于稳定性**：`[send:]` 路由靠 LLM「做完本职主动写标记转交」，在 glm-5.2 上偶尔会断链（成员口头"请查收"却不写标记）。机制本身没错，换更强模型会更稳——详见 3.4 末尾。

## 第 4 章 Subagent vs Team：对比与总结

### 【口播 · 何时用哪个】

| | Subagent | Team |
|---|---|---|
| **适合** | 相互独立的子任务 | 需多角色分工协作的任务 |
| **本质** | 一次性函数（无状态外包工） | 持久对象 + 消息队列协调器（有状态项目组） |
| **触发** | LLM 调 `subagent(role, task)` | LLM 调 `plan_team(members)` |
| **messages** | 独立、用完即销毁 | 独立累积、跨多次 chat 保留 |
| **通信** | 结果只返回主 Agent | 消息队列 + `[send:]` 路由 |
| **调用后** | 主 Agent 继续（汇总多个子结果） | 主循环**直接结束**（团队产出=最终成果） |

**一句话**：Subagent 是**独立拆分**——任务拆成互不相干的子任务，各自做完汇总；Team 是**协作拆分**——任务不拆、拆角色，成员间 `[send:]` 路由转发共同推进。

**为什么 `plan_team` 调用后主循环直接结束？**——`plan_team` 是**终端委派工具**：任务整个交给团队，团队产出即最终成果，主 Agent 不该再插手。所以 `run_agent` 检测到调用了 `plan_team` 就直接 `return` 团队结果，不进下一轮——**用控制流而非 prompt 保证主 Agent 不越权重做**（否则它会自己调 `get_weather` 重做一遍）。subagent 不截断，因为派完还要汇总多个子结果。

### 【口播 · 能力演进】

从 Agent 能力演进看：

```
ReAct       = 会行动
  + Multi   = 会协作
```

demo5 = base × 多 Agent。Subagent 给主 Agent 一个临时工——独立 context，用完即销毁，不污染主 Agent 的 messages；Team 给业务一个正式项目组——多角色分工、消息队列、`[send:]` 路由，解决单 Agent 角色混乱和任务无法流转的问题。
