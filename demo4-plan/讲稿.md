> 本稿配合 `agent.py` + `skills/review.md` 使用。建议讲解节奏：第 1 章 5 分钟，第 2、3 章各 8–10 分钟，第 4 章 10 分钟，全程约 30 分钟。
> 标记说明：
> - **【口播】** = 直接念出来的话
> - **【屏显】** = 配套展示在画面 / 截图里的内容（表格、代码、图）

## 第 1 章 demo4 干了什么

### 【口播 · 开场】

demo1 的 ReAct 循环**走一步看一步**——LLM 每轮只决策下一步。简单任务很优雅，但两个问题：

1. **复杂任务容易跑偏**——走到第 3 步忘了整体目标
2. **高频任务每次重新想**——同样的"代码审查"，每次从零推演，结果还不一样

所以 Agent 需要两个能力：**当前任务的规划**（plan）+ **历史经验的复用**（Skill）。

> ### demo4 = base × 规划

demo1 的核心没动——ReAct 循环、四个本地工具、messages 结构全原封不动。只在上面加了两样，接下来两章分别拆解。

## 第 2 章 机制一：plan（自动决策版）

### 【口播 · plan 是什么】

Claude Code 用户知道 **TodoWrite**——demo4 里我们把它实现成 `plan` 工具。

但 plan 的本质**不是让 LLM 反复管理进度**。它做的事更简单：**LLM 列一次步骤，Agent 打印清单**。

```
LLM                         Agent
  │                            │
  ├─ plan(["A","B","C"])       │
  │                            ├─ 打印编号清单
  └─ 干活（plan 已从 tools 移除）│
```

Claude Code 的 TodoWrite 有完整状态机（pending/in_progress/completed），demo4 刻意不实现——教学最简形态，只做任务拆分和可视化。

### 【屏显 · 代码 2-1 — plan 工具定义】

```python
{
    # === demo4 新增 ===
    "name": "plan",
    "description": (
        "任务规划——仅在复杂的多步任务开头调用一次，列出步骤。"
        "**使用时机**：3 步以上、多工具协作、步骤间有依赖的任务。"
        "简单的一两步任务直接 execute_bash / read_file，不要用 plan。"
    ),
    "input_schema": {
        "properties": {
            "steps": {
                "type": "array",
                "description": "任务步骤列表（动词开头，按执行顺序排列）",
                "items": {"type": "string"},
            },
        },
        "required": ["steps"],
    },
}
```

### 【口播 · plan 的设计】

正向触发（3 步以上）+ 反向抑制（简单任务不要用）。缺一不可。**Planning 本身也是成本**——plan 只调一次，LLM 列完步骤就放手。

### 【屏显 · 代码 2-2 — plan 的实现】

```python
_PLAN: list = []  # 模块级计划列表


def plan(steps: list) -> str:
    """任务规划——仅在复杂多步任务开头调用一次。
    LLM 列步骤，Agent 打印清单。"""
    global _PLAN
    _PLAN = [str(s) for s in steps]
    for i, s in enumerate(_PLAN, 1):
        print(f"  {i}. {s}")
    return f"已规划 {len(_PLAN)} 步"
```

plan 只做一件事：LLM 列步骤（字符串数组），Agent 打印清单。没有状态机、没有进度追踪。调用一次后从 tools 移除——教学最简形态。

## 第 3 章 机制二：Skill（可复用的工作流模板）

### 【口播 · 为什么需要 Skill】

同样的问题让 LLM 做两次，它每次推演的步骤可能不一样——"代码审查"，第一次先读 diff、第二次直接读全文、第三次忘了检查安全性。结果不稳定。

**Skill 把"这类任务怎么做"固化成可复用的模板**：写成一个 markdown 文件，LLM 需要时通过 `use_skill` 获取，按模板执行。

demo4 的 Skill 是 **prompt-based**——不是代码编排，就是一段 markdown 指令，LLM 读到后自己调工具执行。零代码、修改即生效；代价是执行质量依赖 LLM 对指令的遵循度。

这是最简形态的 Skill：单个 md 文件，YAML frontmatter 放元信息，正文即工作流。加载方式也最简——启动时扫目录 → 解析 meta + body → 存内存字典。生产环境的 Skill 可能有代码级编排、多文件打包、版本管理，但核心思路一致。

### 【屏显 · 表格 3-1 — Skill vs 普通工具】

| | Tool | Skill |
|---|---|---|
| **本质** | 能力接口 | 行为规范 |
| **提供** | 执行能力 | 执行策略 |
| **关注** | 怎么做动作 | 怎么组织动作 |

### 3.1 Skill 文件格式

### 【屏显 · 代码 3-1 — skills/review.md 的格式】

```markdown
---
name: review
description: 代码审查工作流——按规范步骤检查代码改动并给出结构化意见
triggers: ["代码审查", "代码评审", "审查代码", "code review", "帮我 review", "review 一下"]
---

# 代码审查工作流

收到「审查代码」类任务时，**必须**按以下步骤执行，不要直接下结论：

## 步骤 1：收集改动
- 如果有 git 仓库：用 execute_bash 跑 git diff 或 git log --oneline -5
- 如果没有 git 或要审整个文件：用 read_file 直接读目标文件

## 步骤 2：逐项检查
| 维度 | 检查点 |
|---|---|
| 命名 | 变量/函数/类名是否清晰、一致 |
| 错误处理 | try/except 是否吞掉异常 |
| 安全 | 命令注入 / SQL 注入 / 硬编码密钥 |
| ... | ... |

## 步骤 3：结构化输出
最终回复必须包含三段：
- ✅ 优点
- ⚠️ 问题（🔴 阻塞 / 🟡 建议 / 🟢 可选）
- 💡 改进建议
```

### 【口播 · frontmatter 三字段】

每个 skill 文件用 YAML frontmatter 声明三件事：

1. **`name`**——skill 的唯一标识（system prompt 元信息 + LLM 调用 use_skill 时引用）
2. **`description`**——一句话说明做什么（启动时被加载到「可用 Skills」元信息段，LLM 据此判断要不要用）
3. **`triggers`**——辅助提示词，放进 system prompt 帮助 LLM 判断任务相关性；最终是否调用 `use_skill` 仍由 LLM 决策

frontmatter 之后的 body 是**真正的工作流正文**——启动时 load_skills() 读入内存字典，LLM 调用 `use_skill` 时通过 tool_result 返回（不直接进 system prompt，避免撑爆上下文）。

### 3.2 Skill 加载器：三个核心函数

### 【屏显 · 代码 3-2 — Skill 加载器】

```python

def _parse_frontmatter(text: str) -> tuple:
    """简易 YAML frontmatter 解析（只支持 name/description/triggers 三字段）。
    不引入 PyYAML 依赖——教学代码保持零额外依赖。"""
    # 用正则匹配首尾 ---，再分别抽取 name/description/triggers
    ...


def load_skills() -> dict:
    """扫描 skills/*.md，解析 frontmatter，返回 {name: {description, triggers, body}}"""
    skills = {}
    for fname in sorted(os.listdir(SKILLS_DIR)):
        if not fname.endswith(".md"):
            continue
        with open(os.path.join(SKILLS_DIR, fname), "r", encoding="utf-8") as f:
            raw = f.read()
        meta, body = _parse_frontmatter(raw)
        name = meta.get("name") or fname[:-3]
        skills[name] = {"description": ..., "triggers": ..., "body": body}
    return skills
```

### 【口播 · 不引入 PyYAML 的设计取舍】

注意 `_parse_frontmatter` 用正则实现简易 YAML 解析，而不是 `import yaml`。这是个有意的取舍：

- **优点**：零额外依赖，复制 agent.py + skills/ 目录到任何机器都能跑
- **代价**：只支持 `name: str` / `description: str` / `triggers: [str, ...]` 三个字段，不支持嵌套结构


### 3.3 system prompt 的渐进加载

### 【屏显 · 代码 3-3 — build_system_prompt + build_skill_metadata_section】

```python
def build_skill_metadata_section(skills: dict) -> str:
    """生成 system prompt 里的「## 可用 Skills」段——只放元信息，不放 body"""
    if not skills:
        return ""
    lines = ["\n## 可用 Skills\n"]
    for name, info in skills.items():
        lines.append(f"- **{name}**: {info['description']}")
        if info["triggers"]:
            lines.append(f"  - 触发词: {', '.join(info['triggers'])}")
    lines.append("\n当用户任务匹配某个 skill 时，先调用 `use_skill` 获取该 skill 的详细工作流，然后严格按要求执行。")
    return "\n".join(lines) + "\n"


def build_system_prompt(skills: dict) -> str:
    """
    构造 system prompt（两层叠加）：
        1. 基础说明（角色）
        2. 可用 Skills 元信息（name + description + triggers，不含 body）
    """
    system_prompt = [
        "你是一个有用的助手，可以通过工具与本地系统交互完成任务。",
    ]
    skill_meta = build_skill_metadata_section(skills)
    if skill_meta:
        system_prompt.append(skill_meta)
    return "\n".join(system_prompt)
```

### 【口播 · 两层 + use_skill 工具 = 渐加载分离】

和 demo1 不同，system prompt 只放两样东西——基础说明 + Skills 元信息（name + description + triggers）。**skill 的 body 不进 system prompt**，而是通过 `use_skill` 工具让 LLM 主动拉取：

| 组件 | 内容 | 何时加载 |
|---|---|---|
| **system prompt** | 基础说明 + 所有 skill 的 name/description/triggers | 每次 run_agent 构造（元信息很小，100 个 skill 也才几百 token） |
| **use_skill 工具** | LLM 调用后返回对应 skill 的 body | LLM 自主判断何时调用（body 走 tool_result 进 messages） |
| **skill 文件** | 完整工作流正文 | 启动时 load_skills() 一次性读入内存字典 |

**为什么不让所有 skill 的 body 都常驻 prompt？**

skill 一多就会撑爆上下文（每个 body 几百到几千 token）。元信息每个 skill 一两行，body 只在 LLM 觉得需要时才通过 `use_skill` 拉取进 messages——这就是"渐加载分离"：system prompt 告诉 LLM"有哪些技能"，LLM 自己决定"要不要拿详细步骤"。

LLM 看到 system prompt 里的"当用户任务匹配某个 skill 时，先调用 `use_skill`"这条指令，自己做语义判断。用户说"帮我 review 一下"，LLM 看到元信息里有 `review` skill 且触发词含"帮我 review"，就主动调 `use_skill("review")` 拿 body。

这是一种**动态上下文注入**：system prompt 只放元信息，body 通过 `use_skill` 按需拉取。不常驻 prompt，skill 再多也只增加少量元信息开销。

### 3.4 视角抬升：Skill、workflow 与 agent

讲完 Skill 的实现，退一步看它在"agent 大图"里的位置。

Skill 是"把这类任务怎么做固化成可复用模板"——这其实就是 **workflow（工作流）思想**：不靠 LLM 现想，人提前把步骤定好。但 demo4 的 Skill 是 **prompt-based 的"软 workflow"**：步骤写成 markdown 注入 prompt，LLM 读到后**仍在 agent loop 里自主执行**，可以偏离、跳过。如果把步骤**从 prompt 下沉到代码**——用 Python 把路径写死，不让 LLM 决定顺序——就变成了"硬 workflow"。

**【屏显 · 代码 — 同一任务两种写法】**

任务：用户反馈分类后回复。`llm(prompt)` 是 `client.messages.create(...)` 的简写，聚焦看结构。

agent 写法（mini-agent 全系列在做的）：

```python
for _ in range(MAX_ITER):
    resp = client.messages.create(messages=messages, tools=TOOLS)
    if resp.stop_reason != "tool_use":
        break
    dispatch(resp)   # 走哪条路、几步、何时停——全是 LLM 现决定的
```

workflow 写法：

```python
category = llm("分类(退款/bug/咨询)，只回类别：" + feedback)   # ① 一定先分类
if category == "退款":                                          # ② Python 路由
    reply = llm(REFUND_PROMPT + feedback)
elif category == "bug":
    reply = llm(BUG_PROMPT + feedback)
else:
    reply = llm(FAQ_PROMPT + feedback)
send(reply)                                                     # ③ 一定发送
```

workflow 这段代码写死了五件事：**顺序**（分类 → 路由 → 回复）、**分叉**（`if` 是 Python 判断、不是 LLM 判断）、**用哪个 prompt**、**步数**（就 3 步）、**何时停**（代码跑完即结束）。而 agent 里这五件事全交给 LLM 在 loop 里现决定——自由换来了不可预测。

**【口播 · 取舍】**

Anthropic《Building Effective Agents》的建议很干脆：**能用 workflow 解决的，就别用 agent。**

- 能**画出任务流程图**（先 X 再 Y，条件 Z 走 W）→ **workflow**（可预测、便宜、好调试）
- 步骤**依赖中间结果、没法预判**（如"修这个 bug"）→ **agent**

回到 demo4：Plan 是 **agent 自己拆任务**（动态拆），Skill 是 **人提前写好的软指导**（静态拆但 LLM 自主执行），硬 workflow 是 **人提前拆死在代码里**。mini-agent 全系列教你做 agent，但记住——**agent 是最后的手段，不是默认选项**。

## 第 4 章 真实演示案例

> 以下三个场景分别对应「简单任务跳过 plan」「复杂任务 plan 列步骤」「Skill 触发」。

### 4.1 场景 A：简单任务——LLM 自动跳过 plan

**用户输入**：

> 统计当前目录下 .py 文件的数量

**实测轨迹（共 2 轮，LLM 未调 plan / use_skill）**：

```
第 1 轮: execute_bash("find . -maxdepth 1 -name '*.py' | wc -l")
         → 工具结果: 1

第 2 轮: end_turn → 助手: 当前目录下共有 1 个 .py 文件
```

### 【口播 · 关键观察】

1. **LLM 没有调 plan**——判断这是简单任务，直接 execute_bash
2. **LLM 也没有调 use_skill**——system prompt 里有 review skill 元信息，但 LLM 判断任务不匹配，跳过

### 4.2 场景 B：复杂任务——plan 列步骤

**用户输入**：

> 我需要你做几件事：1) 先读 agent.py 找出所有工具名称和函数名；2) 然后把这些信息整理成表格；3) 最后写入 inventory.md 并验证。注意第2步依赖第1步的结果，第3步依赖第2步。

**关键轨迹（共 5 轮，plan 仅在第 1 轮调用）**：

```
第 1 轮: plan({"steps": ["读取 agent.py，提取所有工具名称和函数名",
                        "将提取的信息整理成 Markdown 表格",
                        "写入 inventory.md 并验证文件内容"]})
         → Agent 打印清单，plan 从 tools 移除

第 2 轮: read_file("agent.py")

第 3 轮: write_file("inventory.md", ...)

第 4 轮: read_file("inventory.md") 验证

第 5 轮: end_turn → 任务完成
```

（完整日志见屏幕。）

### 【口播 · 关键观察】

- **LLM 只调一次 plan**——列出步骤，后续不再管
- **plan 调后即移除**——LLM 后续轮次看不到这个工具

### 4.3 场景 C：Skill 触发——review 工作流自动激活

**用户输入**：

> 帮我 review 一下 agent.py 这个文件

**关键轨迹（共 5 轮）**：

1. **第 1 轮**——LLM 看到 system prompt 里 review 元信息（触发词含「帮我 review」），主动调 `use_skill("review")` 拿 body
2. **第 2–4 轮**——按工作流执行：git log/diff（无 git 仓库）→ read_file 读 agent.py
3. **第 5 轮**——end_turn，输出结构化报告：✅ 优点 / ⚠️ 问题（P0/P1/P2 三级）/ 💡 改进建议

（完整日志和报告见屏幕。）

### 【口播 · 关键观察】

- **LLM 自己决定何时用 skill**——system prompt 元信息引导，LLM 做语义判断
- **流程一致性**——同一个人无论问多少次 review，LLM 都按同样的模板输出
- **Skill = 可复用的标准流程**：不依赖 LLM 每次从零推演

## 第 5 章 总结

demo4 = base × 规划。在 demo1 的 ReAct 之上加了两样：

| | plan | Skill |
|---|---|---|
| **作用** | 这次怎么做 | 这类事该怎么做 |
| **范围** | 单次任务，结束即丢弃 | 跨任务复用，文件持久存在 |
| **触发** | LLM 按复杂度自动判断 | LLM 看到元信息后自主调用 use_skill |

从 Agent 能力演进的角度看：

```
ReAct       = 会行动
  + Plan    = 会分解复杂任务
  + Skill   = 会复用经验
```

demo1 让 Agent 有了手脚和心跳，demo4 让它有了规划能力和经验库。
