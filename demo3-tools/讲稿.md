# Demo3 教学讲稿 — 工具扩展轴

> 本稿配合七文件结构使用：`agent.py`（主入口）+ `tools.py` / `mcp.py`（MCP 客户端层）+ `render.py` / `memory.py` / `session.py` / `commands.py`（继承 demo2）+ `mcp_server.py`。建议讲解节奏：每章 4–5 分钟，全程约 30 分钟。
> 标记说明：**【屏显】** = 配套展示在画面 / 截图里的内容（表格、代码、图）。

---

## 第 1 章 结论：demo3 比 demo2 多了什么

demo1/demo2 的本地工具（execute_bash / read_file / write_file / edit）都是同进程函数调用。真实 Agent 需要调用**外部工具**——数据库查询、API 调用、第三方服务。每接一个新工具就改一次 agent.py 不现实。

所以 Agent 需要一个标准化的工具协议：**MCP（Model Context Protocol）**——工具跨进程、跨语言、跨机器复用。

### 【屏显 · 表格 1-1 — demo3 vs demo2】

| 维度 | demo2 | demo3 |
|---|---|---|
| **本地工具集** | 4 个 | **不变** |
| **ReAct 循环 / 会话模型** | ✅ | ✅ **不变**（会话持久化 / MEMORY.md / 记忆回顾 / caching 全继承） |
| **自动压缩** | ✅ run_agent 循环前查阈值 | ❌ **去掉**——压缩只由 `/compact` 手动发起 |
| **MCP 远程工具** | ❌ | ✅ 启动握手 + 发现 + 统一分发，Server 不可用时降级仅本地 |
| **命令** | 8 个 | 9 个（+ `/tools` 看工具清单） |

### 代码层的变化

demo2 六文件 → demo3 七文件：**新增一个层，微调两个文件，其余原样继承**。

### 【屏显 · 表格 1-2 — 代码层的增改】

| 文件 | demo2 | demo3 的变化 |
|---|---|---|
| `mcp.py` ★新增 | — | **MCP 客户端层**：`MCPClient`（握手 / 发现 / 调用）+ `discover()`（含降级） |
| `agent.py` | 主循环 | 工具集改为「本地 + MCP 合并」；`_dispatch_tool` 统一分发（本地函数 or MCP RPC）；**删掉自动压缩阈值检查** |
| `commands.py` | 8 个命令 | + `/tools`（本地 / MCP 来源标注） |
| `memory.py` | 记忆层 | 删 `COMPACT_THRESHOLD_MESSAGES` 与 `force` 参数——`compact_messages` 仅手动调用，其余机制原样 |
| `tools.py` / `render.py` / `session.py` | 工具 / 渲染 / 会话 | **原样继承** |

注意第一行——**Agent 进程零新工具代码**。add / multiply / weather 三个新工具的 schema 和实现全在 `mcp_server.py` 里，Agent 只是学会了「发现」它们。这就是工具扩展轴的本质：**能力长在 Server 端，Agent 靠协议接入**。

## 第 2 章 MCP 协议：从函数调用到 RPC

### demo2 工具的局限

demo2 的工具都是**本地函数**：

```python
AVAILABLE_FUNCTIONS = {
    "execute_bash": execute_bash,
    "read_file":    read_file,
    "write_file":   write_file,
    "edit":         edit,
}
```

它有一个天然限制：**工具必须存在 Agent 进程内部**。如果工具来自——另一个团队维护、另一种语言实现、独立部署服务——传统方式只能继续改 Agent 代码。

**MCP 解决的问题：如何让 Agent 动态发现并调用外部工具。**

MCP 不关心工具运行在哪里，它解决的是 Agent 如何**发现**工具、**理解**工具、**调用**工具的问题。

### 【屏显 · 表格 2-1 — 本地工具 vs MCP 工具】

| 维度 | 本地工具（demo2） | MCP 工具（demo3） |
|---|---|---|
| **载体** | Python 函数 | HTTP 服务（任何语言） |
| **发现方式** | 看 `tools.py` 源码 | 调 `tools/list` 拿 schema 列表 |
| **调用方式** | `fn(**args)` 函数调用 | POST JSON-RPC `tools/call` |
| **位置** | 同进程 | 同机 / 跨机 / 跨云 |
| **扩展** | 改代码、重启 Agent | 加一个 MCP server，Agent 自动发现 |

### 2.1 JSON-RPC 2.0：MCP 的传输协议

MCP 用的传输协议叫 **JSON-RPC 2.0**——本质就是 **HTTP POST + 约定格式的 JSON**。

### 【屏显 · 表格 2-2 — JSON-RPC 2.0 请求 / 响应格式】

**请求**（Agent → MCP Server）：

```json
{
  "jsonrpc": "2.0",
  "id":      1,
  "method":  "tools/call",
  "params":  {"name": "add", "arguments": {"a": 2, "b": 3}}
}
```

**响应 · 成功**：

```json
{"jsonrpc": "2.0", "id": 1, "result": {"content": [{"type": "text", "text": "5"}]}}
```

### MCP 三大核心 method

本 demo 只实现 MCP 的 tools 能力，因此涉及三个主要交互：

### 【屏显 · 表格 2-3 — MCP 三大核心 method】

| method | 中文名 | 作用 |
|---|---|---|
| `initialize` | 握手 | 协议版本协商、能力声明 |
| `tools/list` | 工具发现 | 返回完整工具 schema 列表 |
| `tools/call` | 工具调用 | 按 `name` + `arguments` 执行，返回 `content` 包装结果 |

### 【屏显 · demo3 整体架构】

```
                  LLM
                   |
               tool_use
                   |
           +-------+-------+
           |               |
     Local dispatcher    MCP Client（mcp.py）
           |               |
     Python fn         JSON-RPC
                           |
                      HTTP POST
                           |
                      MCP Server（mcp_server.py）
                           |
                    add / multiply / weather
```

LLM 只管发 `tool_use`，由 Agent 端的 `_dispatch_tool` 决定走本地函数还是 MCP 远程调用。两条通道对 LLM 完全透明。

## 第 3 章 MCP Server 实现（mcp_server.py）

### 3.1 工具定义（schema + 实现）

每个工具仍然是「schema + fn」两件套——demo3 把本地工具的 schema 设计成接近 MCP schema（都用 `input_schema` 字段），因此可以低成本合并。唯一的区别：它们不被 Agent 进程直接 import，而被一个独立的 HTTP 服务持有。

### 【屏显 · 代码 3-1 — 三个工具的 schema + 实现】

```python
TOOLS = [
    {
        "name": "add",
        "description": "计算两个数字的和",
        "input_schema": {                      # 与 agent.py 本地工具统一用 input_schema
            "type": "object",
            "properties": {
                "a": {"type": "number"},
                "b": {"type": "number"},
            },
            "required": ["a", "b"],
        },
    },
    # multiply / weather 同构，schema 略
]

def fn_add(a, b):
    return a + b

# 路由表：工具名 → 实现函数
TOOL_FUNCTIONS = {"add": fn_add, "multiply": fn_multiply, "weather": fn_weather}
```

**这一层和 demo1/demo2 完全一样**——schema 描述能力、fn 实现能力、字典做路由表。MCP 没有重新定义工具能力，它定义的是工具发现、调用和交互协议。

### 3.2 JSON-RPC Handler（三大 method 分发）

Handler 接收 JSON-RPC 请求，按 `method` 字段分发到三个内部函数。

### 【屏显 · 代码 3-2 — handle_request 主分发】

```python
def handle_request(payload: dict) -> dict:
    method = payload.get("method")
    req_id = payload.get("id")
    params = payload.get("params", {}) or {}

    try:
        if method == "initialize":
            result = _handle_initialize(params)
        elif method == "tools/list":
            result = _handle_tools_list(params)
        elif method == "tools/call":
            result = _handle_tools_call(params)
        else:
            # JSON-RPC 标准错误码 -32601 (Method not found)
            return _error(req_id, -32601, f"未知方法: {method}")

        return {"jsonrpc": "2.0", "id": req_id, "result": result}

    except Exception as e:
        # 标准错误码 -32603 (Internal error)
        return _error(req_id, -32603, f"服务端内部错误: {e}")
```

### 【屏显 · 代码 3-3 — 三个 method 的实现】

```python
def _handle_initialize(params):
    """握手：协议版本协商 + 能力声明"""
    return {
        "protocolVersion": "2024-11-05",
        "capabilities": {"tools": {}},
        "serverInfo": {"name": "demo3-mcp-server", "version": "1.0.0"},
    }

def _handle_tools_list(params):
    """工具发现：返回完整 schema 列表"""
    return {"tools": TOOLS}

def _handle_tools_call(params):
    """工具调用：name + arguments → 执行 → content 包装返回"""
    name = params.get("name")
    arguments = params.get("arguments", {}) or {}

    if name not in TOOL_FUNCTIONS:
        raise ValueError(f"未知工具: {name}")

    fn = TOOL_FUNCTIONS[name]
    value = fn(**arguments)                          # ← 关键：跨进程 RPC 与本地函数的衔接点

    # MCP 协议规定 tools/call 返回值用 content 数组包装（便于多模态扩展）
    return {"content": [{"type": "text", "text": str(value)}]}
```

### 3.3 HTTP Server 入口

用标准库 `http.server` 起一个 HTTP 服务，所有 JSON-RPC 走同一个端点 `/mcp`。

### 【屏显 · 启动 MCP Server】

```bash
$ python mcp_server.py
============================================================
Demo3 MCP Server 已启动
监听:   http://127.0.0.1:8888/mcp
协议:   JSON-RPC 2.0 over HTTP Transport
工具:   add, multiply, weather
============================================================
等待 Agent 调用...
```

**就这么简单**——MCP Server 的本质就是一个 HTTP 服务，按 JSON-RPC 协议处理三个 method。

## 第 4 章 Agent 端：MCP Client + 工具合并（mcp.py）

Server 端讲完，回到 Agent 端。demo3 新增 `mcp.py`，装两样东西：

1. **MCPClient**——把 JSON-RPC 调用封装成 Python 方法
2. **discover()**——启动时握手 + 发现工具，Server 不可用时降级

### 4.1 MCPClient：把 JSON-RPC 调用包装成方法

每次手写 JSON-RPC 请求太繁琐。封装成一个 `MCPClient` 类，把「组装 payload / POST / 解析响应 / 错误处理」全部藏在 `send()` 里，再在 `send` 之上封三个对应 MCP 三大 method 的方法。

### 【屏显 · 代码 4-1 — MCPClient 三层封装（mcp.py）】

```python
class MCPClient:
    def __init__(self, url: str):
        self.url = url
        self._id = 0

    def send(self, method: str, params: Optional[dict] = None) -> dict:
        """发送一次 JSON-RPC 2.0 请求并返回 result 字段"""
        payload = {
            "jsonrpc": "2.0",
            "id":      self._next_id(),
            "method":  method,
            "params":  params or {},
        }
        resp = requests.post(self.url, json=payload, timeout=30)
        data = resp.json()
        if "error" in data:
            raise RuntimeError(f"MCP 调用失败 ({method}): {data['error']}")
        return data.get("result", {})

    # ---- 三个上层封装 ----
    def initialize(self) -> dict:
        """握手：协议版本协商 + 拿 server 能力声明"""
        return self.send("initialize", {...})

    def list_tools(self) -> list:
        return self.send("tools/list", {}).get("tools", [])

    def call_tool(self, name: str, arguments: dict) -> str:
        result = self.send("tools/call", {"name": name, "arguments": arguments})
        return "\n".join(b["text"] for b in result["content"] if b.get("type") == "text")
```

这三层封装让 MCP 调用看起来就像普通 Python 方法——`mcp.list_tools()`、`mcp.call_tool("add", {"a":1,"b":2})`——但底层每一次都是完整的 JSON-RPC 往返。

### 4.2 discover()：启动发现 + 降级保护

### 【屏显 · 代码 4-2 — discover 与降级】

```python
def discover() -> tuple:
    """启动时握手 + 发现工具。Server 未启动时降级为仅本地工具模式。"""
    mcp_client = MCPClient(MCP_URL)
    try:
        info = mcp_client.initialize()
        mcp_tools = mcp_client.list_tools()
        return mcp_client, mcp_tools
    except Exception as e:
        print(f"[MCP] 连接失败，降级为仅本地工具模式。原因: {e}")
        return mcp_client, []
```

**降级是设计要点**：远程工具箱是增强，不是依赖——Server 挂了 Agent 照样能跑（仅本地 4 工具）。

### 4.3 工具合并：一行 `+` 搞定

启动时一次性拉取 MCP 工具列表，与本地工具合并，得到完整工具集。**整个会话内不变**。

由于本地工具 schema 与 MCP 对齐（都用 `input_schema`），合并就是**直接 `+` 拼接**——不需要任何包装函数或格式转换。

### 【屏显 · 代码 4-3 — 工具合并就是一行 +（agent.py main）】

```python
MCP_CLIENT, mcp_tools = mcp.discover()
ALL_TOOLS = TOOLS + mcp_tools          # 直接拼接，完事
```

### 为什么这么简单

这就是 schema 设计对齐的好处——本地工具和 MCP 工具的结构一致（都是 `{name, description, input_schema}`），对大模型来说没有任何差异。合并不需要函数、不需要转换、不需要标记来源。**一行 `+` 就够了**。

> **真实 MCP 协议规范用的是 `inputSchema`（驼峰）**。demo3 因为演示简化了设计，两端统一用 `input_schema`，省掉字段名转换。

### 【屏显 · 表格 4-1 — 合并后的完整工具列表（7 个，/tools 命令可见）】

| 来源 | 工具名 | 用途 |
|---|---|---|
| 本地 | `execute_bash` | 执行 shell 命令 |
| 本地 | `read_file` | 读文件 |
| 本地 | `write_file` | 写文件（整文件覆写） |
| 本地 | `edit` | 精确替换文件中的一段文本 |
| MCP | `add` | 加法 |
| MCP | `multiply` | 乘法 |
| MCP | `weather` | 天气查询 |

### 4.4 统一分发：`_dispatch_tool`

主循环里工具调用统一交给 `_dispatch_tool`，**它只负责本地 or MCP 二选一**。

### 【屏显 · 代码 4-4 — 统一分发器（agent.py）】

```python
def _dispatch_tool(name: str, args: dict) -> str:
    """统一工具分发：本地 or MCP。LLM 不需要知道工具在哪，只按名字调用。"""
    if name in AVAILABLE_FUNCTIONS:
        try:
            return str(AVAILABLE_FUNCTIONS[name](**args))     # 本地：函数调用
        except Exception as e:
            return f"[错误] 本地工具 {name} 执行失败: {e}"

    try:
        return MCP_CLIENT.call_tool(name, args)               # 远程：JSON-RPC POST
    except Exception as e:
        return f"[错误] MCP 工具 {name} 调用失败: {e}"
```

### 关键观察

注意——**对大模型来说，调用本地工具和调用 MCP 工具是完全一样的体验**：都是 `tool_use` 块、都拿到 `tool_result`。路由差异全藏在这个分发器里，**把「工具在哪」这个工程细节从 LLM 的视野里抹掉**。

## 第 5 章 与 demo2 的差异 + 真实案例

### 5.1 为什么去掉自动压缩

demo3 继承了 demo2 的全部记忆能力（会话持久化、MEMORY.md 模型自主维护、任务结束回顾、caching），**唯独去掉了自动压缩**——主循环不再查阈值，压缩只由 `/compact` 手动发起。

原因很简单：**工具轴的教学焦点是协议，不是窗口管理**。demo2 已经把压缩讲透了；demo3 的演示任务都很短，自动压缩永远不会触发，留着阈值检查反而添噪。`/compact` 手动路径保留——想演示压缩随时可以手动触发。

### 5.2 真实案例：5 步任务的一气呵成

用一个**故意混用所有工具类型**的任务把整章讲过的东西串起来——本地 bash、本地 write/edit、MCP 算术、MCP 天气（2026-10-08 实测，rich 渲染）。

任务如下：

```
1) 如果有 weather.txt，先删除；
2) 计算 35+47；
3) 计算上一步的结果 × 9；
4) 查询上海天气并写入 weather.txt；
5) 修改 weather.txt 里面的上海为北京。
```

### 【屏显 · Agent 启动】

```
[MCP] 握手成功：{'name': 'demo3-mcp-server', 'version': '1.0.0'} 协议版本 2024-11-05
[MCP] 发现 3 个远程工具：add, multiply, weather
[Tools] 合并后共 7 个工具：execute_bash, read_file, write_file, edit, add, multiply, weather
```

启动三件事：MCP 握手成功、7 个工具合并、若 MCP 没启动则降级为仅本地工具模式（4 个工具照常可用）。

### 【屏显 · 真实运行日志（关键轨迹）】

```
第 1 轮
stop_reason = tool_use
⏺ tool_call   | execute_bash({'command': 'rm -f weather.txt'})
⏺ tool_call   | add({'a': 35, 'b': 47})            ← 本地 + MCP 同轮并行
✔ tool_return | [命令执行成功，无输出]
✔ tool_return | 82

第 2 轮
⏺ tool_call   | multiply({'a': 82, 'b': 9})        ← 82 来自上一轮 add 的 tool_result
⏺ tool_call   | weather({'city': '上海'})
✔ tool_return | 738
✔ tool_return | 上海 今天天气：多云，气温 22°C

第 3 轮
⏺ tool_call   | write_file({'content': '上海 今天天气：多云，气温 22°C', 'path': 'weather.txt'})
✔ tool_return | [成功] 文件已写入: weather.txt (18 字符)

第 4 轮
⏺ tool_call   | edit({'new': '北京', 'old': '上海', 'path': 'weather.txt'})
✔ tool_return | [成功] weather.txt 替换 第 1 处（共 1 处）

第 5 轮
⏺ tool_call   | read_file({'path': 'weather.txt'})  ← LLM 主动验证
✔ tool_return | 北京 今天天气：多云，气温 22°C

第 6 轮
stop_reason = end_turn
● assistant   | 5 步汇总表（全部 ✅，最终内容：北京 今天天气：多云，气温 22°C）
[记忆] 任务结束回顾：无需更新                     ← demo2 继承的记忆机制在跑
```

### 5.3 五个关键观察

| # | 观察 | 启示 |
|---|---|---|
| 1 | **第 1 轮并行 2 个工具**（execute_bash + add），第 2 轮又并行 2 个（multiply + weather） | LLM 判断任务之间不存在依赖，一次返回多个 tool_use，Agent runtime 依次执行 |
| 2 | **同一响应里本地 + MCP 混调** | 路由差异全藏在 `_dispatch_tool`，LLM 视角下 7 个工具调用体验完全一致 |
| 3 | **第 2 轮 multiply 直接复用 add 的 82** | 共享 messages 让 LLM 拿到上一轮 tool_result，跨轮状态自然传递 |
| 4 | **第 4 轮 edit 只发 `old='上海'` + `new='北京'`** | 没 read 整文件、没 write 整文件——token 成本 O(改动大小) |
| 5 | **第 5 轮 LLM 主动 read_file 验证 + 任务结束回顾「无需更新」** | 好的 Agent 会主动自检；记忆回顾继承自 demo2，无持久事实时不写 |

这一个案例覆盖了 demo3 的全部能力：本地四件套 + MCP 三件套 + ReAct 主循环的并行 / 状态传递 / 自主验证。**用户只写一段自然语言，LLM 自己拆任务、并行、路由、收尾**。

## 第 6 章 总结

demo3 = base × 工具扩展。在 demo2 的记忆底座上，把工具从「同进程函数调用」扩展为「跨进程协议」——JSON-RPC + 独立 Server，Agent 启动时自动发现工具，LLM 无需知道工具在哪。

从 Agent 能力演进的角度看：

```
ReAct       = 会行动
  + 记忆    = 会记得过去（demo2）
  + MCP     = 会接外部工具（demo3）
```

还有一种完全不同的思路：**让 LLM 直接输出可执行代码**，agent 在本地跑掉（smolagents 的 CodeAgent、ChatGPT 的 Code Interpreter 走的就是这条路）。它更紧凑——一段代码能表达循环 / 条件 / 对象传递，比「一轮一个 tool_call」省步数；但 LLM 写的代码要真执行，**带来远多于结构化 tool_call 的不可控风险**，必须配沙箱兜底。demo3 选 tool_use 这条路，就是为了把「LLM 能干什么」限定在预定义的 schema 里——可控性优先。
